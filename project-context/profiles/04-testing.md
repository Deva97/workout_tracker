## 3. Development Testing Skill & Quality Gate Runner
Development testing in this project is strictly governed by the [flutter-development-testing](file:///Users/devashishraut/StudioProjects/workout_tracker/.agents/skills/flutter-development-testing/SKILL.md) skill. Testing is always-on, continuous, and non-bypassable.

### 3.1 Testing Layers & Standards
1. **Layer 1: Static Analysis Quality Gate**:
   - Command: `flutter analyze`
   - Exit Criteria: **0 errors, 0 warnings, 0 lints**.
   - Zero Tolerance for Lint Suppression: Inserting `// ignore:` or `// ignore_for_file:` is strictly prohibited without vetted architectural justification.
2. **Layer 2: Hermetic Unit Testing**:
   - 6-step workflow: Arrange -> Act -> Assert -> Verify State Invariants -> Boundary/Edge Cases -> Failure/Exception Handling.
   - Hermetic mocking with `SharedPreferences.setMockInitialValues({})` and in-memory `WorkoutDbContext`.
   - Comprehensive boundary validation (zero reps, negative weights, boundary RIR, extreme values).
3. **Layer 3: Observable Widget & UI Component Testing**:
   - Asserts user-visible behavior (rendered text, badges, dialogs, gestures) rather than private widget state.
   - Full UI state lifecycle coverage: Initial, Loading, Empty, Populated, Error, and Rollback states.
4. **Layer 4: Cross-Layer Integration Testing**:
   - Verifies end-to-end flows: `UI -> ViewModel -> Use Case -> Repository -> DbContext/ExcelORM -> DriveService`.
   - Validates authentication, sheet creation prompts, transactional rollbacks, and date navigation.
5. **Layer 5: Conditional Android Native Testing**:
   - Triggered upon changes to `android/`, native Kotlin code, `AndroidManifest.xml`, or Gradle configurations.
   - Executes manifest validation and headless debug build: `flutter build apk --debug --no-pub`.
6. **Layer 6: Regression Testing Protocol**:
   - Mandatory 5-step protocol for bug fixes:
     1. Reproduce failure with an isolated test.
     2. Verify failure against unmodified code.
     3. Implement minimal production code fix in `lib/`.
     4. Verify test passes against fixed code.
     5. Run full test suite (`flutter test`) and permanently retain the regression test.

### 3.2 "Cheapest First" Execution Sequence
To optimize latency and developer velocity, tests are run in cost-optimized order:
1. `flutter analyze` (~1s) - Static analysis fast fail.
2. Targeted unit test (`flutter test test/<target>_test.dart`) (~1-2s).
3. Targeted widget test (`flutter test test/<widget>_test.dart`) (~2-3s).
4. Impacted test suites from Test Impact Map (~3-5s).
5. Full project regression suite (`flutter test`) (~6-10s).
6. Conditional Android native build (if native code modified).

### 3.3 Failure Classification Taxonomy
When any test fails, it must be triaged into one of five standard categories before resolution:
- `PRODUCT_CODE_FAILURE`: Defect in `lib/` implementation code. Action: Fix production code; do not weaken test.
- `TEST_FAILURE`: Test asserts outdated contract after approved feature evolution. Action: Update test and document rationale.
- `ENVIRONMENT_FAILURE`: Missing SDK, toolchain discrepancy, or lockfile conflict. Action: Resolve environment or run `flutter pub get`.
- `PRE-EXISTING_FAILURE`: Test was already failing prior to the changeset. Action: Isolate, document, and report separately.
- `INFRASTRUCTURE_FAILURE`: Flaky timing, mock timeout, or unpumped async future. Action: Make test deterministic with `tester.pump()`.
