## 1. Overview
The project follows Clean Architecture principles, separated into Domain, Data, and UI layers. It relies heavily on a custom Excel ORM for data persistence over Google Drive and strictly decoupled MVVM ViewModels in the UI layer.

## 2. Current Implementation
### 2.1 Clean Architecture Implementation
The application segregates responsibilities cleanly:
- `lib/domain/` houses pure business rules (models, repository interfaces, use cases like `GetTodaysWorkoutUseCase`, `ManageWorkoutSetUseCase`, `GetExerciseStatisticsUseCase`).
- `lib/data/` contains repository implementations (`WorkoutRepositoryImpl`, `ExerciseRepositoryImpl`, `WorkoutSplitRepositoryImpl`) and services (`GoogleDriveService`, `LocalStorageService`), along with a custom ORM in `lib/data/orm/` for Google Sheets.
- `lib/ui/` is split into `core/` (shared widgets, theme) and `features/` (feature-based organization with views and `ChangeNotifier` ViewModels).

### 2.2 Workout Log MVVM Decoupling
In the Workout Log feature:
- `TodaysWorkoutLogScreen` is fully decoupled from `GoogleDriveService` singleton, consuming `TodaysWorkoutLogViewModel` which orchestrates use cases (`GetTodaysWorkoutUseCase`, `ManageWorkoutSetUseCase`, `ManageExercisesUseCase`, `WorkoutRepository`).
- `ExerciseStatisticsScreen` is decoupled from direct drive queries and bound to `ExerciseStatisticsViewModel`, computing strength chart metrics, timeframe filtering, and in-memory query caches.
- Both screens accept optional constructor-injected ViewModels, allowing 100% hermetic unit and widget testing without real Drive connections.

### 2.3 Repository Pattern
The repository pattern isolates data access concerns effectively. A strong example is the `WorkoutRepository` interface, which defines distinct data access strategies: `getWeeklyDailyRecords()` serves as a read-only query method that bypasses the underlying `GoogleDriveService` purge policy, while other methods handle active data mutation. This abstracts the cache management details away from the domain layer.

## 3. Patterns & Conventions
- **Clean Architecture**: Strict Domain, Data, and UI separation.
- **MVVM Pattern**: ViewModels (`ChangeNotifier`) manage UI presentation logic, exposing getters and notifying listeners.
- **Repository Pattern**: Abstract interfaces in Domain, implemented in Data layer.
- **Constructor Injection**: ViewModels and Use Cases accept injectable dependencies with fallback defaults.
